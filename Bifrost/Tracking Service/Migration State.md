### D. Persistence: Firestore → MongoDB Atlas (2026-11-06)
Why: the 2026-11-06 burst errors (G3 below), the ~40/s cap from shared counter docs, 40 composite indexes whose absence fails a query, and counters kept correct only by `recompute-stats`. Shape: stats are aggregated over a narrow per-record `marks` collection, so no shared document remains; each write is a Mongo transaction over one record's own docs (the event-doc check is the only guard against a redelivered first sighting being counted as a copy); cutover is a **hard cut** (2026-11-06, Harry): rollback subscriptions are created, prod ingest is held so Firestore stops changing, Firestore is imported into Mongo and parity-checked against the frozen copy, `STORE` flips and the hold is released; every message lands on exactly one side of the cut. A `seen` collection makes every Mongo write exactly-once. Draft and three reviews: 2026-11-06 session.

## Risks
- **R1 ★ Zero-loss cutover** — ingest is held so the new subscriptions build a backlog, and event ids are Pub/Sub message ids (the same on every subscription), so replay is idempotent. The hold drained in ~12 minutes on both envs — closed 2026-10-14.
- **R2 ★ New indexes exist only in the new database** — anything that needs one (date sorts, windows) must not ship against the legacy stack. Default queries and the lane filters use the existing indexes — standing.
- **R3 Metrics that don't exist yet** — percentile tag configs for `fuse.tracking.*` can't be created before the new stack emits them, configured after cutover in B7 — closed 2026-10-15.
- **R4 Per-connector failure rule** — a delivery that names no connector clears every connector's earlier failure, because fan-out publishes the made message without one. A single connector behaves exactly as before — accepted and shipped with C6, 2026-10-15.
- **R5 Held-duplicate links** — the deduper keys a held order on its own id, which can differ from the customer reference. The link is matched on exact references so it is absent rather than wrong — standing.
- **R6 Tracker page verified without sign-in** — the page was checked against prod data and locally, never signed in by an agent. Jack signed in and verified the first round. Later releases haven't had that second pair of eyes — open.

- **R7 ★ Copy-redelivery horizon** — a record remembers its last 64 counted copy ids (`dedupe.go:22`), about 1.5–2 h of PURDYFIGG resends. A held backlog older than that, relative to when the record is imported, replays as new copies and inflates `duplicates`. D11 keeps the hold-to-import window inside it, or the import skips copies older than a watermark — **closed by design 2026-11-06**: the hard cut means no message is applied on both sides, and the `seen` collection makes Mongo exactly-once regardless of the window.
- **R8 ★ Redelivery is not idempotent without the event doc** — `recordContentIn` counts a re-applied first sighting as a copy; only the event-doc check in the same transaction stops it. Every Mongo write is a transaction over one record's docs — open.
- **R9 Served stats move to recompute-equivalent values** — see G5 — open.
- **R10 Timestamp precision** — Firestore keeps µs, BSON dates ms; `deliveries.go` compares at µs. Check prod `publishTime` precision; fallback int64 µs — open.
- **R11 Shadow observability** — metrics are tagged only `service:<project_name>`; a second service from the same root double-counts dashboards and monitors, and held subs trip the backlog composite — D7 — open.
- **R12 No Firestore backup** — prod PITR is off and Firestore holds the only copy of the frozen `duplicates` history — G4, G11 — open.
- **R13 `redrive` re-applies under a new messageId**: Pub/Sub doesn't carry the original id onto a DLT message, so a partly-applied message that is redriven is re-applied as a republished copy and inflates copy counts. It's pre-existing and also affects Firestore. A fix would carry the original id through an attribute — open.
- **R14 One order can split across two records** when a message lacks the customer ref: `~SO:` fallback, a Shopify failure keyed by the raw `name`, a replay-service edited failure, or normalisation gaps (BOM, NFD, internal whitespace). Nothing re-keys or merges the stray doc. **Live data 2026-11-06: 0 fallback-keyed docs and 0 duplicate businessId + customerRef groups in dev (34,294) and prod (89,156)**, so this is latent. The fix is code (merge a fallback doc when its ref arrives), not an index — open, low.

## Scar tissue
- **Identity is businessId + customer reference** — the derived Snap ShipmentId is display and search only, never a join key.
- **Count a record once, on its first failure** — counting each flip of a derived flag turned one Saira order into 57 failures and the headline into 76 against 15. Never count a flip.
- **A human runs `recompute-stats` and the backfills against prod, never an agent** — dry-run first, with ingest held. This was broken on 2026-10-07 (three runs, each with a dry run and ingest held) and is recorded here so it isn't repeated.
- **Recompute must diff every counter, reason code and duration bucket** — it once skipped a day whose totals already matched, and stale per-business reason codes survived (`0585898`).
- **Lane-filtered attention pages must read on until the page is full** — the attention query is ordered oldest-due first and the lane filter ran after each page, so Running late came back empty behind older failures (`e17d9b9`).
- **Don't push to `main` while a Deploy run is in flight** — a push cancelled the image jobs in both runs.
- **Approving the fuse-ui prod gate ships everything on `main` since the live sha** — check `git log` first and cancel older parked runs afterwards.
- **A failed lookup is never "no failure"** — cross-service lookups degrade by omitting the link, never by counting zero.
