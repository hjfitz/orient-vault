## What this is
Re-shaping the confirmation handling of `snap-queue-polling-service` (repo `gfs-bifrost/snap-adapter`,
`apps/snap-queue-polling-service`) from eight self-contained per-type handlers into one staged pipeline
with three tracks (shipments, receipts, stock movements) written as data. **Zero external-contract
change** — topics, attributes, envelopes, claim key, Firestore store, and the SNAP call pattern per type
stay identical. The framing is *declarative, not extensible*: the type set is fixed, so the win is that
the behaviour can be read from the track literals and operated on with confidence. Review:
https://claude.ai/artifact/UMpV4iouA7bTv3hVv9PyR8. No Jira ticket by Harry's choice.

> SUPERSEDED 2026-11-03 — the claim key is no longer part of the contract (the Redis claim was deleted by #308), and the black-box counts are no longer 56 / 21 / 40 / 11. See the 2026-11-03 Decision log entry; U0 re-derives both against `master`.

Invariants every unit holds: behaviour-preserving on `master`; black-box call counts re-derived (with the
arithmetic written down) rather than patched; golden-master canonical outputs unchanged; no abstract
`Stage`/engine/registry types — tracks are literals, stages are functions. The end state, stage order,
shapes and reviewer checklist are in [[Confirmation Enrichment Pipeline/Target Design|Target Design]] —
read it before planning a unit.

## Scar tissue
- **Read the queue once per transaction type**, never once unfiltered — `$top` is per request and one backlogged type would starve the others (INC-30 scenario). The track runner keeps one read per track per business.
- **Handlers/mappers never touch the queue or Redis or Pub/Sub.** FUSE-876's review rejected an ambient per-poll cache (`AsyncLocalStorage`) precisely because a handler's dependency on "someone already fetched this" was invisible in its signature — enrichment must be explicit input to a mapper, never ambient.
- **Claim key is `confirmation-claim:{businessId}:{queueId}`** (FUSE-1176); `queueId` alone collides across tenants.
- **A routing-store read failure fails that page for the cycle and rethrows; it never degrades to broadcast.** `snap.routing_lookup.{hit,fallback_attachment,miss}` are the drain gauge for eventually deleting the attachment read — keep them meaningful.
- **Absent `confirmationsEnabled` is not-enabled** (fail closed) — safe only because of the FUSE-1063 prod backfill; do not loosen.
- **The goods-out/goods-in alias asymmetry is deliberate** — goods-in retags to `goods_in_confirmation`, goods-out keeps `goods_out_confirmation` because shopify-connector's live subscription filters on it. Data, not a branch; not this programme's to change.
- **`stock_adjustment` carries no routing and is broadcast by design**; it must not be flagged manual-origin.
- **Publish happens before the stage-2 ack** (600s ack deadline) — the whole fetch → map → publish must fit one invocation; the pipeline must not add a third Pub/Sub hop.
- **The black-box harness counts every unmatched mock route as a SNAP call** — any new config-service read needs a mock route *and* an exclusion in `tests/mock-server.ts`.
