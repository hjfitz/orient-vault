## Risks
- **R1 ★** Registrar NS flip — a propagation window in which resolvers split between old and new NS sets, for every public hostname on the domain — *mitigation*: dual-hosting; both zones serve identical answers for the whole window, so the split is invisible — *status*: strategy chosen; verified by Bd2/Bp2.
- **R2 ★** Drift during the window — a service's record changes (e.g. a new LB IP) land in the old zone via its Terraform while the seeded copy in the new zone goes stale, and becomes the authoritative stale answer after the flip — *mitigation*: freeze gate (G3/G3p), keep the window short, re-run the diff as the last action before the flip — *status*: open until Bd4.
- **R3 ★** Nameserver shard collision — both old zones sit on `ns-cloud-e{1..4}.googledomains.com`. Cloud DNS assigns the shard; if the new zone for the same `dns_name` also lands on `e`, it is **unknown which zone those shared nameservers answer for** — and if the effect were instantaneous, "stop after creating" would be too late. Reasoning against it: Cloud DNS's multi-shard design exists so a same-named zone in another project can't capture a delegation — a zone on a non-delegated shard is inert — which implies same-name zones are placed on different shards. Strong reasoning, not a verified doc statement — *mitigation*: check the docs first (A1 notes); run A1 on **dev** as a watched operation with live `dig` and delete-the-empty-zone as a seconds-fast revert; record the assigned set; stop if `e*`. Prod inherits whatever dev proves — *status*: open until A1.
- **R9** Registrar typo at the flip — a wrong nameserver entered at the registrar is total NXDOMAIN for the domain, not a slow degradation — *mitigation*: `dig +trace` within minutes of the change; the old set is written down and is the rollback (Bd3/Bp3 notes) — *status*: captured.
- **R10** Old zone deleted while resolvers are still sticky on it — *mitigation*: G6 (elapsed time + query-count metric), not just "all C merged" — *status*: gate added.
- **R4** Registrar identity unverified (see G2) — *status*: open.
- **R5** Per-repo divergence — four repos hardcode a bucket (C02, C01 dev; C15, C16 prod), C13 has preview-env state routing, C03 has override variables, C15 is a direct-to-master repo — *mitigation*: captured per unit in Notes; C01 pilot first — *status*: captured.

## Scar tissue
- **No mutation of a record in the OLD zone before that domain's propagation gate (G4/G5) is ticked** — the old zone is still authoritative for some resolvers until then.
- **C units are state-only.** A plan that shows a DNS create or destroy is wrong; stop and fix the `import`/`removed` blocks rather than apply it. An in-place ttl/rrdatas update is fine; a replace never is.
- **Never `gcloud dns record-sets import --delete-all-existing`.** It replaces every rrset in the target zone — it would wipe A1's records (and, on the wrong zone, the live domain). Plain additive import only.
- **Don't seed (Bd1/Bp1) until the C batch is prepared.** The seed opens the drift window; the batch closes it. Seeding early to "get ahead" lengthens the only realistic downtime path for nothing.
- **Registrar NS flips (Bd3, Bp3) need explicit confirmation from Harry** — one-way doors with a propagation lag on revert.
- **`ilg.software` waits on the dev pilot (C01).** Do not seed the prod zone to "get ahead" — it opens the R2 window for prod with nothing to show for it.
- **`ilg-platform/core-infra` resource names carry `var.env`** — both env state paths hit the same project (`root.hcl`).
- **`ilg-secure-notes` (C15) is direct-to-master** — a push *is* the prod deploy, so G5 gates the push itself.
