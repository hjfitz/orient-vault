# history-prior-art — Early-consume feasibility study (2026-09-29)

Label: history-prior-art. Read-only investigation. Sources read: Waypoint vault, Confluence (Bifrost space), Jira FUSE, GitHub PRs (snap-adapter, snap-queue-polling-service archived), Slack thread (read-only), Datadog metrics (prod, 7d), source at snap-adapter origin/master @ 3c1578b and sftp-connector origin/master @ f6a15e3.

## 0. Headline findings

1. **There is no design doc or ticket that records a decision to "clear on confirmation_made rather than on find".** I found no evidence that "consume on find" / "mark processed at poll" / an outbox or durable ledger was ever proposed or rejected (searches: vault, Jira, Confluence, gh PR search on "mark processed", "outbox", "consume on find", "clear on publish"). The current design is the *default that grew*: the very first commit of the poller's clear-down (archived repo `gfs-bifrost/snap-queue-polling-service` d7c2813, 2025-07-24, Harry Fitzgerald, "feat: clears down outbound queue") wired `confirmation_made` -> `PATCH /v2/snapoutbound/{queueId}/processed`. Before that the handler was a stub that logged "confirmation made". So "clear once the downstream has acked" was the founding shape, later copied per record type (FUSE-973 RGA PR #117, FUSE-892 pick/pack PR #138, FUSE-876/1062 WOC/FGR, FUSE-1059 PO/SO cross-entity made subs PR #229; FUSE-1184 stock_adjustment still queued as Ready for Refinement).
2. **The OBQ-as-safety-net is now *documented, load-bearing behaviour*, not an accident.** Confluence "Snap Polling Service" runbook (page 38993931) states: SNAP host down -> "Confirmations are delayed, not lost — items stay in the OBQ"; Pub/Sub publish failing -> "items remain in OBQ and re-publish on retry"; hanging items "Not lost — stuck ... will publish itself on a later poll"; the queue-clear step swallows errors and "the item stays in the OBQ and is re-seen next poll". The FUSE-1063 design ("an ineligible confirmation stays claimable in SNAP's outbound queue and is picked up automatically once the connector's config catches up") and CLAUDE.md ("A successful confirmation is published and left on the queue - cleared by the downstream confirmation-made flow, not here. This is central to INC-30") make it explicit. Changelog 2026-08-13: the WOC `confirmation_made` subscription is "load-bearing: an emitted confirmation is left on the Snap queue by design and would republish once the dedupe claim lapses".
3. **The single strongest structural argument FOR early consume is INC-30 itself**: postmortem (Confluence 230490121) lists "Slow, multi-hop clear-down - re-fetch within the redelivery window always returns the same items" as a contributing factor; customers with automated processing (Stubble, SportLux) were disrupted by duplicates. Customer impact of duplicates is real and documented (FUSE-1257 text: "most automated setups follow the Inovize standard and don't expect duplicates, so it can break their processing").
4. **The strongest arguments AGAINST are prior incidents where the re-announce loop was the ONLY recovery** (INC-33 SAIRA, FUSE-1238 poisoned source, FUSE-1118 PURDYFIGG live today, FUSE-1144 STUBBLE, Jitterbit-overlap drain) and a direct precedent for the ack-early failure class (FUSE-1104: dedupe acked before processing -> ~54,300 records silently lost in a dev load test; fixed to ack-last / at-least-once on 2026-08-17).
5. **Motivation candidates**: re-announce/claim-skip churn is large (prod 7d: ~52k `claim.duplicate` + ~58k `claimed_entry_skipped`) but it is concentrated in a handful of permanently-stuck rows/businesses nobody delivers (SISTACO not live, STUBBLE, PURDYFIGG stock_move, EPARFUM). Early consume would silence that churn — by discarding rows nobody ever delivered. It would NOT fix the dominant log-volume item (87% = StU-not-found warn on ~4,207 un-mappable consignments; those rows never reach announce).
6. **Existing defect that matters**: the SNAP `PATCH .../processed` clear-down trusts a 2xx. PR #189 (FUSE-1062, verify the clear-down actually happened; documents SNAP answering 2xx `{Status:"Error"}` and entries staying `DateProcessed: null`) was **CLOSED unmerged on 2026-08-25**, and origin/master `clearFromOutboundQueue` (snap-adapter `adapters/confirmations/confirmations.service.ts:18-24`) still just issues the PATCH and discards the response. Any early-consume design that reuses this call inherits a silent-false-success primitive.

## 2. Was early consume / outbox ever proposed?

- Searched: vault (`outbox`, `consume on find`, `mark processed (at|on|when)`, `early consume`, `clear at publish`) -> zero hits outside this study. gh search PRs snap-adapter for "mark processed", "processed on publish", "clear on publish", "outbox", "consume on find", "clear at poll", "clear immediately" -> zero results. Jira JQL text searches (outbound queue / OBQ / clear-down / re-announce / mark processed / DateProcessed / snapoutbound / outbox-ish terms) -> no ticket proposing it.
- Nearest thing: Confluence "Outbound Queue" (39026791) documents PATCH after Pub/Sub publish confirmation (never how code behaved). And FUSE-996's note that claim TTL should expire so a failed clear-down retries.
- Nearest durable-ledger prior art: replay-service (`confirmation_data_failure` inbox, Retry Queue) and collector (transaction-history lifecycle) — both are *observers*, not delivery guarantors. FUSE-1011 ("[Reliability] Close no-DLQ / silent-drop gaps across collector, replay & egress", Won't do 2026-09-21, "still real and unaddressed" per Harry's own comment) lists exactly the terminal-outcome gaps early consume would depend on: collector subs with no dead_letter_policy; validation-failed pushes ACKed 204 and dropped; replay `create_data_failure` DLT has no subscriber; replay's `confirmation_data_failure` subscription originally filtered only to pick/pack; fapi ACK 204 on total delivery failure; shopify-connector failure path unconfirmed. (Some sub-items have since been fixed piecemeal — see other investigators; the ticket itself is closed as deprioritised.)
- Direct create-side precedent for ack-early: FUSE-1104 (Done): dedupe-service acked 204 first; Mongo pool collapse -> "~54,300 records silently lost ... zero 5xx" in dev load test; fixed by dedupe #122 (2026-08-17) to ack-last/at-least-once. Bifrost/Dedupe NestJS Migration notes: "at-most-once was the old design; at-least-once is the current one". Early consume is at-most-once at the SNAP boundary by construction.

## 3. What the previous system (Jitterbit) did with OBQ rows

- I could not find documentation of Jitterbit's OBQ handling in the vault, Jira or the Bifrost Confluence space. What IS evidenced (Slack thread 1790148725.881649, James Godsell / Danny Williams / Harry): Jitterbit and Fuse can read the **same** SNAP outbound queue (a shared user/host, "the Fuse Snap API host was looking at the Jitterbit queue, instead of having a fuse dedicated queue"); Jitterbit is a competing consumer that marks rows processed; a business "Jitterbit ecom and Fuse wholesale split" exists for several customers; "Fuse can pick up either everything, or nothing" (poll is per business, not per stream). Jack Bailey: those split customers' confirmations were "turned off ... beginning of April" and recently switched on.
- The Jitterbit requirements review (Confluence 1218609153, ilguk space, "Jitterbit Integration Assessments Consolidated Requirements List", 21 Sep, draft) is cited from FUSE-1145 but was not readable via this Atlassian site; it may document Jitterbit's acknowledgement/error semantics. -> open question.
- Implication: on a shared queue, any Fuse-side "mark processed at find" removes the row from Jitterbit's view. Today the FUSE-1063 gate keeps un-owned rows on the queue "for Jitterbit to pick up". Early consume must therefore sit strictly AFTER every eligibility/ownership gate (business poll gate, connector gate, cross-tenant BizId gate, and a not-yet-existing STOCK_MOVE ownership gate).

## 4. Customer/SLA promises

- No documented SLA or "no confirmation is ever lost" promise found. Closest statements: Confluence Outbound Queue page ("processed exactly once where possible"); Snap Polling Service runbook ("delayed, not lost"); snap-queue-polling-service known-context.md ("self-healing, not data-losing" — explicitly *because* the OBQ backs up and drains after recovery); FUSE-1145 (record outcome notification: customers migrating from Jitterbit expect an acceptance/error signal; "Failures delivering outbound confirmations back to the customer" is listed OUT of scope there); FUSE-1257 (support must not be able to cause duplicates via Retry Queue; automated customers "don't expect duplicates"). Incident-driven customer commitments: INC-30 remediation was per-customer, "replay clean files only where the customer confirms they're needed".
- The invariant the EM states ("we can't lose these") is therefore a NEW, stricter contract than any documented today; today's real guarantee is "at-least-once via OBQ, with duplicates bounded by a 10-min Redis claim".

## 5. Motivation candidates and whether early consume would address them

| `snap.outbound.claimed_entry_skipped` | 57,884 | STUBBLE despatch 18,181; PURDYFIGG despatch 16,596 + stock_move 16,420; EPARFUM despatch 4,512; WILDSMITH 1,056; DISCOVERED 768 |

| `snap.confirmation.hanging` | 2 | negligible |

So re-announce noise is real, but it is a *small set of stuck rows re-announced ~5 times/hour forever*. Early consume would eliminate the churn — and would do so by discarding rows that no connector delivered. Each of those populations is a different loss/no-loss decision:
- SISTACO (not live), GADG `gone`, BFA ineligible: intentionally undelivered ("disabled connector = deferred, enabling releases the backlog"); with early consume the rows must remain unconsumed (gate before consume) or the deferral feature is destroyed.
- STUBBLE/PURDYFIGG/EPARFUM rows: several are the FUSE-1238 poisoned-source class (repaired 09-24) and Shopify stock_move/goods-out stuck rows (FUSE-1118 class).
- SNAP Polling Log Volume programme (Bifrost/SNAP Polling Log Volume): baseline 395,752 logs/day; 87% (345,517) = one StU-not-found warn for ~4,207 consignments across 19 businesses that "never resolve and re-poll every 2 min forever"; 12,431 raw error pair; 22,167 info chatter; 8,850 debug. Claim-related lines (B1: "Confirmation claim skipped duplicates" 733/day + "Skipping already-claimed queue items" 512/day) = ~0.3% of volume. Early consume would remove B1's lines but NOT A1: StU-unmatched consignments fail enrichment BEFORE announce, so "consume at announce/publish" never touches them; "consume at raw find" would clear them without ever producing a confirmation = loss (and the programme deliberately excludes root-causing why SNAP never returns a StU).
- Recurring "stuck row blocks the lane" pain (FUSE-1144, three occurrences, 63h weekend outage on 09-11) was fixed differently (per-record isolation, #227); the residual poison record "stays queued and re-reports each poll" by design.
- Duplicate-to-customer pain (INC-30, FUSE-1062 unverified clear) — early consume genuinely reduces the duplicate surface (no dependency on the slow multi-hop clear-down, no dependency on SNAP honouring PATCH after delivery) IF consume happens once and reliably at find time.
- Cost/noise from `withheld_*`/re-enrichment: FUSE-1063 #240/#241 already cut ~14/30 businesses and pre-enrichment claim skips.

Verdict on motivation (facts only): early consume would fix duplicate-delivery risk and claim-churn noise; it would not fix log volume (87% unrelated), stuck-lane blocking (already fixed), or any delivery-side error class (it makes those *terminal-or-lost* instead of *retried forever*).

## 6. Exit paths where TODAY'S recovery depends on the row staying on the OBQ (with what early consume would do)

See structured output for the machine-readable table. Summary of evidenced paths:

1. Connector delivery throws / swallowed (`Promise.allSettled`) — shopify-connector INC-33, FUSE-1118 (still Backlog, live today PURD133D2FB4FD8): no `confirmation_data_failure`, 0 replay rows; recovery = re-announce after manual data fix. Early consume: lost, unrecorded.
2. No matching delivery subscription / wrong `source` attribute — FUSE-1238: never delivered or cleared; repaired by data fix, delivered from OBQ. Early consume: lost (Pub/Sub message with no subscriber is not retained anywhere).
3. sftp-connector: no eligible target (`use_case_inactive`, connector inactive, no username, no mapping, EDI envelope missing) -> logs + metric `fuse.confirmation.unroutable`, returns; no made, no `confirmation_data_failure` (confirmation-egress.service.ts L~150-165 @ f6a15e3). Recovery today = re-announce once config is fixed. Early consume: lost, metric-only.
4. sftp-connector all-invalid batch: fixed by #282 (now publishes failures); pre-fix emitted made-with-empty-list. Stock adjustments: one bad record rejects the whole bulk envelope (204, nothing written) — still open per Harry's PR note.
5. Downstream connector `confirmation_made` decode failure in snap-adapter (`handleConfirmationMade` returns 202 first; decode error -> log only, message acked): row stays on OBQ and re-announces; early consume moves that to n/a (no clear needed) but any decode failure in the *connector's* ready-side handling becomes the loss point. fapi #120: bulk `confirmation_made` "silently fails their Zod boundary and gets acked away with no retry and no failure event ... three goods-in receipts stuck re-polling forever, no alert" (fapi architecture note).
6. Snap-adapter clear-down false success (SNAP 2xx + `Status:Error` / entry stays unprocessed): today -> duplicate delivery (self-heals on later poll); early consume: the consume PATCH itself can silently fail -> duplicate announce AFTER the durable state says consumed, or loss if the poller trusts the false success and drops its own retry state. #189 closed unmerged.
7. SNAP host outage / breaker open / 5xx on enrichment: rows stay; "delayed, not lost". Early consume must not consume before enrichment/publish success.
8. Pub/Sub publish failure in stage 2: `poll_customer` redelivers (600s ack) and rows remain; with early consume a consume-before-publish crash = loss.
9. Stage-2 crash / Cloud Run eviction mid-poll (after some groups published): today safe (re-announce, claim dedupes); early consume mid-cycle = partially consumed batch with unpublished remainder.
10. Redis unavailable: claim fails OPEN -> duplicates (INC-30 class); not loss.
11. Connector withheld (unresolved/ineligible) -> "left claimable ... picked up automatically once config catches up" (FUSE-1063): a deliberate deferral feature (GADG `gone` 10,991/7d; BFA ineligible 2,584/7d; SISTACO).
12. Shared queue with Jitterbit / co-tenants (cross-tenant BizId guard, STOCK_MOVE unguarded): consuming another tenant's or Jitterbit's row = loss for them.
13. Manual-origin broadcast (no connectorId/source): broadcast to all connectors; publishes an informational failure (`no_originating_connector`) that FUSE-1257 says should NOT be stored/retried.
14. Failure-path recording gaps: replay `confirmation_data_failure` sub filter history (FUSE-1011), DLT with no consumer (`create_data_failure` DLT, snap-adapter create_record DLT — "orders are actually lost", vault snap-adapter/known-context.md), collector pick/pack lifecycle not tracked (FUSE-1208 Ready for Development).
15. Poison / never-enrichable rows (StU never returned, ~4,207 consignments; FUSE-1144 residual): stay queued forever, re-reported; early consume cannot reproduce today's "visible forever" — it would either lose them or need an explicit quarantine terminal state (FUSE-1144: "needs a product decision on retry/quarantine policy").

## 9. Note on the Confirmation Enrichment Pipeline programme (in flight)

The "announce" seam in Target Design pins "claim -> publish -> clear" ordering and states clear only for zero_quantity/cancelled drops; the programme's contract pin says the claim key, TTL, 600s ack, and the SNAP call set stay byte-identical. Early consume would be a change to that contract (announce would gain a consume step). U7 ("announce owns side effects", high risk, opus/high) is the natural seam. Risk R2 there already flags INC-30 ordering. Programme decision (2026-09-18) frames the goal as readability not extensibility.
