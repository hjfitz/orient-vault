## 1. Lifecycle, end to end (all file paths under apps/snap-queue-polling-service/src)

1. Trigger. Cloud Scheduler cron `*/2 * * * *` (`iac/.../variables.tf` poll_schedule default) publishes "trigger" to the schedule topic; push sub (ack 20s) -> `POST /event/poll/schedule` (`http/controllers/event.controller.ts:98`) -> `PollingService.registerCustomerForConfirmations` (`core/polling/polling.service.ts:81`).
2. Fan-out. `getAllConfiguredBusinesses` (`core/config/remote-config.provider.ts:62`) keeps businesses with any connector `confirmationsEnabled===true` or `broadcastConfirmations`; skipped businesses are never read that cycle (info log + `snap.poll.skipped_ineligible_business`). Fails open to "poll everyone" if the business index is unreadable. Chunked by `CUSTOMER_CHUNK_SIZE` (app default 2, terraform default 5, no tfvars override so prod = 5); one `poll-customer` Pub/Sub message per chunk (`polling.service.ts:97-129`). Business with no backend config or empty host is silently dropped from the chunk (`polling.service.ts:113`, `user-config.utils.ts:9`).
3. Stage 2. Customer-poll sub (ack deadline 600s, no retry policy, no DLQ: `iac/.../pubsub.tf:69-96`) pushes to `POST /event/poll/confirmations` (`event.controller.ts:116`) -> `PollingService.handleConfirmations` (`polling.service.ts:132`): `getConfirmations` then `announceConfirmations`, all synchronous before the 204. Cloud Run has no `timeout` set in `cloud-run.tf`, so the request timeout is the platform default (300s), not the 600s ack deadline.
4. Drain (`core/snap/confirmations/outbound-queue.drain.ts`, `queue-lane.ts`). Three lanes (DESPATCH, RECEIPT, STOCK_MOVE). Per lane, per business client, one `GET /v2/snapoutbound?$top=1000&$filter=Transaction eq '<lane>'` (`adapters/snap/api.client.ts:194`). No `$skip`, no `$orderby`, no `DateProcessed` filter, no lock/lease semantics: the GET is non-destructive; the only state change is `PATCH /v2/snapoutbound/{XDoc}/processed`. (Spec: `snap-api.openapi.yaml:11463-11600`; `/next` exists, unused.) Presumably SNAP omits processed rows from the list; nothing in the client filters them (open question).
5. Pre-filter `dropClaimed` (`queue-lane.ts:178`): peeks `confirmation-claim:{businessId}:{XDoc}` in Redis; a hit drops the row before enrichment. Lookup error = unclaimed.
6. Resolve (`outbound-queue/{despatch,receipt,movement}.entries.ts`, `batch-fetch.ts`): parse the row `Key` (Zod, throws on malformed), batch-search the owning entity (`/v2/shipments` or `/v2/receipts`, 25 ids per OData request, `$top` = ids in the filter), cross-tenant drop by `BizId` (trim+case-fold, absent BizId keeps the row). STOCK_MOVE: per-row `GET /v2/stockmovements/{Move}` in pages of 50, `Promise.all`.
7. Handlers (`*.confirmation-handler.ts`, `despatch-` / `receipt-confirmation.handler.base.ts`): each consumer on a lane gets the same resolved entries and filters by ownership predicate (stage + OrderType/OrderClass). Per page of 50: Firestore routing store `getAll` (routing-aware types), then per-entry enrichment fetch inside `mapEntriesInIsolation` (`Promise.allSettled`). Enrichment fetches per type:
   - good_out: `/v2/stockconsignment`, `/v2/stuconsignment`, `/v2/despatchstock/{id}`, `/v2/attachments/SHL|SHH/{id}` (all throwing; any failure = entry skipped).
   - good_in: `/v2/stockconsignment` per consignment id (failures swallowed via `partitionSettledPromises`), `/v2/attachments/REH` (throwing).
   - pick: `/v2/attachments/SHH`, `/v2/stockdetail` (throwing). pack: same plus `/v2/stuconsignment` (throwing).
   - RGA: `/v2/stockdetail` and `/v2/attachments/REH`, both try/caught and degraded (log event only).
   - WOC: `/v2/attachments/SHH` (throwing); paired R10 receipt search up to 3x, failures swallowed (warn) and degraded to components-only.
   - FGR: none. stock_adjustment: none beyond the per-row movement fetch in resolve.
8. Canonicalise/validate/group (`confirmations.service.ts:74-153`): per type, `confirmationsToCanonical` -> `validateCanonicalConfirmations` (Zod safeParse, invalid records filtered with warn + metric) -> `groupByCustomer` (key customer+connectorId+source, customer from `bizId`/`businessId`/movement `BizId`) -> keep only groups whose customer is in the chunk's enabled customers (exact string match) -> `resolveRoutingSources`.
9. Connector gate `resolveRoutingSources` (`confirmations.service.ts:155`): for groups with `routing.connectorId`, resolve source (config-service, cache-first) and `confirmationsEnabled`; not enabled and no `broadcastConfirmations` -> group withheld; connector gone/unavailable -> withheld unless `broadcastConfirmations`; any other error rethrows.
10. Announce (`confirmations.service.ts:271`): sequential per group: claim each record (`SET NX PX`, key `confirmation-claim:{businessId}:{queueId}`, TTL `REDIS_CONFIRMATION_CLAIM_TTL_MS` default 600000 = 10 min; not set in `cloud-run.tf`), drop "duplicate", fail open on "unavailable"; then ONE `topic.publishMessage` for the whole group (`record` = array of confirmations; `pubsub.router.ts:104,140`); then, if the type expects provenance and the group has no source/connectorId, publish one informational `no_originating_connector` `BifrostFailure` per record to `confirmation_data_failure`.
    - Topics/attributes: good_in -> `confirmation_ready` recordType=goods_in_confirmation; good_out -> recordType=goods_out_confirmation; RGA/pick/pack/FGR/WOC -> `confirmation_ready` recordType=<own name>; stock_adjustment -> `stock_adjustment_ready`, no recordType attribute (`bootstrap/factory/controller.factory.ts:39-85`). Extra attributes: `source` (resolved channel), `broadcast="true"` when no origin or `broadcastConfirmations`. Envelope `{record: T[], metadata:{customer, correlationId, timestamp(unix s), source?, recordType, connectorId?}}`. Note good_in/good_out are NOT registered under their own names, so the legacy per-entity publish is gone; the app's CLAUDE.md still describes a dual publish (stale).
    - `metrics fuse.confirmation.published` is incremented in `claimConfirmations` (`confirmations.service.ts:392`) BEFORE the publish, so it counts claims, not accepted publishes.
11. Nothing in the poller marks a row processed, except the two "clear on drop" cases inside handlers (`ConfirmationDisposer`, `confirmation.disposer.ts`): goods-in with zero received quantity (`goods-in.confirmation-handler.ts:105`) and goods-out shipment `Status==01` cancelled (`goods-out.confirmation-handler.ts:85`). A clear failure is caught, logged, swallowed; the row stays and is retried next poll.
12. Row clear for successes: snap-adapter `POST /confirmation/made/:recordType` -> `PATCH /v2/snapoutbound/{queueId}/processed` (`apps/snap-adapter/src/http/controllers/event.controller.ts:178-235`, `adapters/confirmations/confirmations.service.ts:18`). Outside this area (other investigators).

## 2. Answer: what stops a row being re-announced every poll today?

Only two Redis-backed guards, both keyed `confirmation-claim:{businessId}:{queueId}` with a 10 minute TTL, and nothing else:
1. Announce-time atomic claim (`SET NX PX 600000`) is the authority. A second claim inside the TTL returns "duplicate" and the record is dropped from the publish.
2. `dropClaimed` is an optimisation: a read-only peek before enrichment that saves SNAP calls (metered `snap.outbound.claimed_entry_skipped`).

Consequences, all verified in source:
- The guard is time-boxed, not state-based. Once the claim key lapses (10 min = every 5th 2-minute poll) a row still on the OBQ is re-enriched, re-claimed and republished. The OBQ row is the at-least-once retry: an uncleared row is republished roughly every 10 minutes indefinitely until `confirmation_made` clears it. There is no cap and no give-up outcome.
- Claim is taken BEFORE publish and is never released (`IConfirmationClaimService` has no release/delete; `core/cache/types.ts`). A publish that fails leaves a live claim, so the retry waits for the claim TTL to expire, then the OBQ re-presents the row.
- Withheld groups (connector not enabled/unresolved) never reach the claim, so they are re-enriched (full SNAP call set per row) and re-withheld on EVERY poll for as long as the connector is disabled. Prod 7d: `snap.confirmation.withheld_unresolved_connector` sum 10,991, `withheld_ineligible_connector` 2,584.
- Fail-open: Redis unavailable -> `tryClaimConfirmation` returns "unavailable" -> publish anyway (duplicates over loss). Redis is Memorystore BASIC tier (`iac/.../redis.tf`), no replica, so a restart/maintenance empties all claims.
- Prod evidence that the mechanism is load-bearing, not theoretical (7d): `snap.confirmation.claim.duplicate` 52,104; `snap.outbound.claimed_entry_skipped` 57,884; `fuse.confirmation.published` (claim wins) good_out 36,333 + stock_adjustment 4,870 + good_in 32 vs `snap.confirmation_handled` (snap-adapter clears) 16,481. Published outnumbers cleared by roughly 2.5x, which is consistent with republish-after-TTL churn (or rows never cleared); I could not attribute it per row (open question). 52k announce-time duplicates despite the pre-filter also suggests overlapping polls of the same business or pre-read misses; unexplained.

## 4. Key semantic points for the early-consume proposal (facts, not design)

- Nothing in the poller currently produces a durable record of any failure. The only `confirmation_data_failure` publishes are informational `no_originating_connector` business_rule records for broadcast confirmations that were also published (`confirmation-failure.ts:53-83`); Waypoint notes replay may treat them as replayable and collector marks some as failed. Every genuine drop in E1-E39 is log or metric only; none reaches collector or replay-service.
- Success and every enrichment/validation/gate failure share the same "leave it on the OBQ, try again" convention; the OBQ row is the only durable retry state. Redis holds no payload, Pub/Sub publish is fire-and-await with no local retry beyond the client library, and the process has no durable store of its own ("There is no database here", CLAUDE.md).
- Publish-before-ack, claim-before-publish (INC-30/FUSE-996/FUSE-1176) is the pinned ordering; moving the PATCH earlier than publish removes the only retry for E33/E34/E36. PATCH after publish success leaves a duplicate window if the PATCH fails (the poller's own clear path swallows errors, `confirmation.disposer.ts`; the SNAP client retries transient failures twice, `retry.interceptor.ts:MAX_RETRIES=2`).
- A per-row PATCH from the poller must respect: cross-tenant ownership (E11; instance-wide queue; STOCK_MOVE has no owner check), handler ownership (E14), and the connector gate (E28/E29, which today is a deliberate deferral valued by ops).
- The 1000-row window means today unprocessable rows (E10, E14, E23-E25, E27-E29) accumulate on the OBQ and can starve newer rows on a lane; early consume would relieve that but convert each into a loss unless routed to a recorded terminal outcome.
