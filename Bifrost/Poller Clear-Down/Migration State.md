## What this is
snap-queue-polling-service (`gfs-bifrost/snap-adapter`, `apps/snap-queue-polling-service`) clears each
SNAP outbound-queue row itself, right after its confirmation is published, instead of waiting for
snap-adapter to clear it off `confirmation_made`. See [[Poller Clear-Down/Overview|Overview]].

**The invariant every unit holds:** once a row is cleared, the confirmation must end in a recorded
terminal outcome — `confirmation_made`, or a `confirmation_data_failure` that lands in replay-service
with enough routing to be redriven. A path that acks without either is a loss. `stock_adjustment` is
out of scope throughout.

**Broadcast terminal outcome (G5, decided 2026-10-01):** a broadcast stays one publish to every
consumer (a business requirement). Any connector's `confirmation_made` is success. A consumer with ≥1
connector that **takes** the type (has a mapping for it) and does not deliver to it records one failure
per such connector, stamped with its channel (`source`) and `connectorId`, so replay shows which
connector types failed and B1 redrives to that channel only. No connector for the business, or no
mapping for the type, is benign and records nothing. When no connector in any subscribed channel takes
the type, the poller records one unroutable failure itself. With that, broadcast rows are cleared after
publish like routed ones.

> SUPERSEDED 2026-10-01 — the v1 "broadcast rows are never cleared by the poller" sentence below; broadcast rows are cleared once E1's downstream legs and C1/C2's broadcast handling land (see Broadcast terminal outcome above).
**Clear rule (poller):** a row is cleared only when the poller has published *either* its canonical
confirmation *or* a failure record for it. **Broadcast rows** (no `routing.connectorId` — manual-origin, or a `broadcastConfirmations` business) are never cleared by the poller in v1; they stay on snap-adapter's clear-on-made path. Rows that can't be turned into a canonical (mapping or
validation failure, SNAP enrichment error, unknown business) are never cleared. They stay on the OBQ as
today, because raw SNAP shapes can't go on the bus.

## Scar tissue
- **On a `@gfs-bifrost/types` major, upgrade every confirmation consumer (fapi, sftp-connector, shopify-connector) before the poller.** Consumers ack a push that fails their schema (E3), and once a business is allow-listed the poller has already cleared those rows. A poller on a newer major than a consumer turns schema drift into silent loss.
> SUPERSEDED 2026-10-02 — fixed and deployed (snap-mcp#23, `snap-mcp-prod` `6bcd233`). The hosted MCP now serves each tenant its own data. Snap MCP reads made before about 13:22Z today for a second business on a shared host may still be wrong.
- **The snap MCP serves the first caller's tenant.** `snap-mcp-server/src/snap/snap-api.service.ts:57` caches one client per SNAP *host* and ignores the credentials on later calls, so a read or `snap-write` for a second business on a shared instance (ilg001/003/004/005) runs as whichever business called first in that MCP process. Read or write a second business with direct GETs on its own credentials until it's fixed. The outbound queue is per business, not per instance.
- **After processed, the list route never returns the row** — `GET /v2/snapoutbound` only lists open rows (filters on `DateProcessed`/`Stage 90` return `[]`). A processed row is still readable by id (`GET /v2/snapoutbound/{XDoc}`, verified in dev back to 2025-12-15), and XDoc is sequential — that is the only way back. There is no known un-process route.
- **SNAP can return 2xx with `Status:"Error"`** on writes; neither clear path checks the body today (snap-adapter #189, which would have, was closed unmerged).
- **snap-adapter's made handler sends 202 as its first statement**, so a failed clear is never redelivered — today it relies on the row staying on the OBQ.
- **The OBQ is shared with Jitterbit for split customers**, first-to-process wins, no consumer attribution.
- **Claim key is `confirmation-claim:{businessId}:{queueId}`**, claim before publish, never released; queueId alone collides across tenants.
- **Raw SNAP shapes can't go on the bus**, so a row the poller can't canonicalise is never cleared.
- **replay redrive "success" means the publish was accepted**, not delivered.
- **Pub/Sub push backoff under `retry_policy 10s/600s` is slow-growing.** It went 13s → 18s → 24s → 32s → 41s → 60s → ~100s (verified in dev 2026-10-01), so 10 delivery attempts arrive in about 5 minutes. Size `MAX_TRANSIENT_DELIVERY_ATTEMPTS` against that, not against a doubling estimate.
- **The `confirmation_ready` DLT deliberately has no publisher grant.** The `dead_letter_policy` exists only to make Pub/Sub send `deliveryAttempt`. Granting the Pub/Sub agent publish there would forward unrecorded messages to a topic nothing subscribes to.
