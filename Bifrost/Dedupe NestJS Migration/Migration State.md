### On the duplication I expected to extract — and didn't

Roughly 730 lines of the four specs is preamble that *looks* copy-pasted, and my first instinct was to lift it into the harness before merging. I checked, and the evidence said no:

- `salesOrder()` exists in four files with **four different signatures** (options object / positional+overrides / positional+lineCount / positional+skus) — each parameterises what its own spec varies. One shared builder would need five optional knobs, which reads worse at 3 AM than four small obvious ones.
- `pushBody()` has **three** signatures; `waitForPublishes()` **three** implementations (only 2 of 4 byte-identical — admin-api's is nested, differently timed, and reads a different accessor).
- The `pushBody` duplication is also **self-detecting**: if the envelope contract drifts, records get rejected and the file's own tests fail loudly. Silent drift is not a risk here.

So: landed as-is. The durable output is the **harness gap list** below, which is additive work rather than a refactor. Recording the reasoning because "extract the duplication" is the obvious-looking call and it was wrong.

## The traps that will bite (all measured)

1. ~~**`ConfigRevisionException → 200` is unreachable dead code today.**~~ **Closed by #105** — the controller answers 200 itself, so a Nest port no longer flips this behaviour. Original note: Express 4 doesn't route async rejections to 4-arity middleware, so a failed revision returns *nothing* and the push times out. **Under Nest that arm goes live**, flipping failures from redelivered-until-success to acked-and-dropped on a DLQ-less subscription. → E2, needs sign-off.
2. **Nest resolves routes by class-body method order, not static-before-param.** `byId()` before `stats()` → `/api/v1/record/{type}/stats` returns **400** and fuse-ui's Dedupe Summary silently blanks. **Survived contact with reality in R2 (#124):** `record.controller.ts` declares `stats` before `:id`, N5's characterization test guarded it, and the ordering was confirmed live against real dev data rather than by test alone. The trap stays listed — it applies to every future controller, and nothing mechanical prevents a reorder.
3. ~~**A value-returning create handler converts at-most-once → at-least-once.**~~ **RETIRED 2026-08-23 — the conversion already happened, on purpose.** FUSE-1078's [#122](https://github.com/gfs-bifrost/dedupe-service/pull/122) (merged 2026-08-17) rewrote `postRequest` to **ack last**: it awaits `handleCreateRequest`, then answers 204 on success, **503 on a transient failure** (nack, `event.nacked`) and 204 on a permanent one (`event.dropped_permanent`). The original measurement stands as a fact about Nest, but the *behaviour it was protecting no longer exists to protect* — dedupe's create path is now deliberately at-least-once. E3 should therefore use a plain value-returning handler, which is both the Nest-idiomatic shape and the one that matches current behaviour. Do **not** reintroduce `@Res()` on the create route to "preserve" ack-first.
4. ~~**An unguarded post-ack throw destroys the only drop signal.**~~ **RETIRED 2026-08-23, same cause.** With #122's ack-last ordering there is no post-ack work left to throw *past* an already-sent response, so `ERR_HTTP_HEADERS_SENT` is no longer reachable on this path. The `try/catch` that trap 4 called a "declared behaviour addition" is now simply the route's primary control flow, already on `master`, already classifying transient vs permanent — E3 carries it verbatim rather than adding it. **The E3 pre-gate requiring Harry's sign-off on that `try/catch` as a behaviour addition is consequently moot** — he signed off the behaviour itself in #122.
5. **`vi.mock` on a moved path is a silent no-op.** Moving `deep-compare` detaches four specs' mocks, the real `isEqual` runs, and every changed-vs-unchanged branch in 78 tests inverts. Invisible to `tsc` and biome.
6. **`vitest.setup.ts` overwrites `MONGODB_CONNECTION_STRING` unconditionally, after globalSetup, per worker** — so a harness silently hits localhost:27017. Green locally for anyone with a local mongod.
7. **`biome check --write` erases DI.** `lint/style/useImportType` is recommended, fires on the injected-collaborator pattern, and is a *safe* fix — it rewrites the runtime class to a type import and breaks DI while `tsc` stays green.
8. **`NestFactory.create` with `{logger:false}` prints zero bytes and exits 1** on a DI failure. A crash-looping revision with an empty log stream.
9. **`@nestjs/platform-express@11` hard-pins `express 5.2.1` as a direct dep.** S1 implicitly moves the server to express 5; `req.query` parsing changes from `extended` to `simple` unless set back. **Refined 2026-08-11 (S1, fault-injection-verified):** the `bodyParser: false` half of this trap is more precise than "omitting it breaks the 100mb limit" — calling `buildApp()` (which registers its own `bodyParser.json({limit:"100mb"})`) *before* `nestApp.init()`/`.listen()` ever runs already wins the Express middleware-registration race against Nest's default body-parser, so simply removing the flag does **not** reproduce a regression with S1's actual call order. Forcing an early `nestApp.init()` call (simulating a future refactor of `createApp()`) *does* reproduce it — a 413 at Express's 100kb default. The flag is kept as insurance against that future reorder, not because it's load-bearing today; a permanent characterization test (`large payloads`, `create-request.e2e-spec.ts`) guards the invariant either way.
10. **api-key must keep its bare 503** when `API_KEY` is unset (fail closed). Replay's guard has no such arm — its `API_KEY` is required at boot, dedupe's is `.optional()`.
11. **A `@Param` pipe on any `/events` push route converts an ack into a poisoned message.** Measured 2026-08-27 on E1 (Harry asked "no pipes?" in review). A Nest pipe signals failure by **throwing**, and on these routes an unroutable value must ack 204. Built the idiomatic `ParseReleaseRecordTypePipe implements PipeTransform` throwing `BadRequestException`, wired it to `@Param`, dropped the guard, ran the e2e: **`expected 204 "No Content", got 400 "Bad Request"`**. Path: pipe throws → `AllExceptionsFilter` passes the `HttpException` through with its real status → 400 → Pub/Sub nack → **no `dead_letter_policy` on any of the 8 release subscriptions** → redelivers until `message_retention_duration` expires (#118's backoff keeps it off a hot loop; it never drains). A *non-throwing* pipe doesn't help either: a pipe cannot short-circuit a handler without throwing, so the `if (!recordType) return;` branch stays in the controller regardless, and the warn log needs the **raw** segment the pipe would have consumed. **Note the `APP_PIPE` invariant is not what blocks this** — that bans the *global* token, and scoped Nest primitives are already in use (R2's `@UseGuards`, R1/E2's `@UseInterceptors`); the blocker is purely the ack semantics. Applies to E3 (the create route, same class of subscription) and to C2. Separately, `@Body()` pipes stay banned on `/events` for a different reason — a `ValidationPipe`/DTO strips `metadata.capture` (the FUSE-794 class).
    - **Where a pipe *does* belong, as a follow-up:** `record.controller.ts` (R2, merged). `resolveRecordType()` throws `NotFoundException` and `resolveObjectId()` throws `BadRequestException` — genuine reject semantics on an admin API where a 4xx is correct, and the throw already exists. Two hand-rolled private helpers across four handlers; `ParseRecordTypePipe` + `ParseObjectIdPipe` would delete both (Nest's `ParseUUIDPipe` is the exact analogue). Its own small PR, not part of a route conversion.

## 🔴 Bug 31 — NEW, and the most urgent thing in this document

**Any unhandled rejection exits the dedupe process.** `observability/logger/transports.ts` sets `handleExceptions: true` and `handleRejections: true`; `exitOnError` is never overridden and winston defaults it to `true`. Observed directly — a test run hit `process.exit unexpectedly called with "1"` from winston's `rejection-handler.js` `gracefulExit`.

This **escalates bugs 21–24**, which I had recorded as "record lost silently". ## Second batch, 2026-07-29 — PRs #106, #107, #108

**#106 + #107 are a pair that close the unhandled-rejection class**, not two more instances of it. **#108 is unrelated latent infra.**

**#106 — a rejected promise no longer restarts the container.** `consoleTransport` set `handleRejections: true` and the logger is built without `exitOnError`, which winston defaults to `true`, so its rejection handler logged and then `process.exit(1)`. `index.ts` **already** had its own `unhandledRejection` listener, so every rejection was logged **twice** and the second handler killed the process regardless of the first. Winston now handles exceptions only (an uncaught exception leaves the process undefined-state and still exits); `index.ts` logs the rejection and counts it against a new `errors.unhandled_rejection`.

> **`exitOnError` cannot express this.** It accepts a function, but the function receives only the error and is consulted by *both* `exception-handler.js:170` and `rejection-handler.js:171` — so it cannot exit on one signal and not the other.
