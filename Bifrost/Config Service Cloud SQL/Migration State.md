## What this is
config-service moves its persistence from MongoDB Atlas to Cloud SQL for PostgreSQL, through Drizzle, with schema migrations run as a Cloud Run Job inside the same Terraform apply that rolls the service. See [[Config Service Cloud SQL/Overview|Overview]].

**The invariant every unit holds:** the HTTP contract is the thing under test, and the database is swappable behind it. Every one of the 52 `/api/v1` routes answers the same shape, the same `X-Resource-Version`, the same errors, and the same `config_revision` event from either backend. The only differences are the ones listed in the Decision log, on purpose.

## Risks
- **R1 ★ Contract drift** — a response changes shape or order between backends (`_id`, list ordering, date serialisation, numeric types from `jsonb`). Mitigation: A0's fixtures, A4's backend-parametric suite, and D2 run before every cutover with Mongo as the oracle — open.
- **R2 ★ Write loss on a prod rollback** — a write that lands on Postgres after E2 is lost if we flip back. Mitigation: the freeze, the audit-service config-change log as the record, and a one-week soak before anything is torn down — open.
- **R3 ★ A migration runs against the wrong code** — the job and the service drift, or a migration drops what the previous revision still reads. Mitigation: the job runs the service's own image, the apply orders job then revision, B4 blocks a schema change without its migration, and the expand/contract rule in Scar tissue — open.
- **R4 Version regression** — a backfill that resets `metadata.version` makes `X-Resource-Version` go backwards, and remote-config readers compare it. Mitigation: D1 carries the version across; D2 diffs the header — open.
- **R5 Connection limits and cold starts** — the Cloud SQL connector adds a handshake, and Cloud Run instances times pool size can exceed the instance's connection cap. Mitigation: `min_instance_count = 1` already; pool size set in C4; measured in E3 — open.

## Scar tissue
- **The Mongo driver writes `undefined` as `null`** on insert, `$set` and pipeline `$set` alike. A Mongo document can therefore hold an explicit `null` that Postgres reads back as absent, and readers parsing `.optional()` (not `.nullable()`) reject Mongo's version. When parity matters, compare the two as equal. When a schema is involved, fix the producer, as #285 did.
- **Every `pg` client or pool a test opens needs an error listener** (`tolerateTermination()`). A forced database drop terminates idle connections, and an unlistened one fails the whole vitest run after all its tests have passed.
- **Merge a Terraform provider bump after any stack that branch-deploys to dev.** Once `main` applies with the newer provider, dev state is written by it, and a branch based on older `main` runs the older provider against that state on its next manual deploy. M0 (google 7.46.2) merges after the A-group stack for that reason (2026-10-28).
- **No passwords, anywhere.** Every database login is an IAM user through a Cloud SQL connector, and the instance refuses anything else (`connector_enforcement = REQUIRED`, no authorised networks). A `BUILT_IN` user, a `DATABASE_URL` secret or a password in a connection string is a regression, not a shortcut.
- **While a branch with new infra is applied to dev, merge nothing else to config-service `main`.** The `Deploy` workflow's dev apply runs `main`'s Terraform and destroys the branch's resources. With direct VPC egress the subnet destroy fails (`resourceInUseByAnotherResource`, Cloud Run's serverless address holds it), which leaves every later `main` dev apply red. Hit on 2026-10-28 with B1 (#257 merged mid-verification); restored by re-running the branch deploy. Merge the infra unit first.
- **Expand/contract, always.** No migration may drop or rename anything the previous release's code still reads. A column is dropped at least one release after the code stopped reading it, because Cloud Run keeps the old revision serving while the new one starts, and a rollback redeploys the old image without rolling back the schema.
- **The migration job runs the same image as the revision it precedes.** Never a separate build, never a laptop against prod.
- **`drizzle-kit generate` exits 0 when it fails.** Any tooling around it must read its output (`migrations:check` requires "No schema changes" or new files) and must not trust the exit code. It also mangles an absolute `--out`.
- **The migration job runs on every apply, not every image.** Its `run_execution_token` comes from the image plus `GITHUB_RUN_ID`/`GITHUB_RUN_ATTEMPT`. With an image-only token, a re-run of a failed deploy had no job diff and rolled the service onto code whose migration never applied (proven on dev, 2026-10-29). The job's `terminal_condition` stays `Ready` after a failed execution, and the provider (7.46.2) doesn't expose the execution result, so a postcondition can't catch it. Don't "optimise" the token back to the image.
- **`drizzle-kit` is a devDependency.** The runtime migrator is `drizzle-orm`'s. The production image and the `--prod` audit never carry the CLI.
- **The app SA owns no DDL.** Only the migrator SA can change the schema; a bug in the service cannot.
> SUPERSEDED 2026-10-28 — `save`'s guard does match: it keeps the version when the record passed equals the stored document, `_id` and key order included, which is the case whenever a service saves a connector it just read. See the next line.
- **`metadata.version` increments on every write and never resets.** Today's `save` increments on every write because its guard never matches; Postgres does the same explicitly, and the backfill carries the number across.
- **`metadata.version` bumps only when a connector write changes something; every other write bumps it.** Storefront, business, backend, shipment-method, DDP and flag writes pass a fresh DTO, so they always bump. Connector saves (mappings, PATCH, credential cycling) pass the document just read, so an identical write keeps its version, pinned by integration tests since A1 increment 3. C2's connector repository needs an explicit "changed?" check to match; the backfill still carries the number across.
> SUPERSEDED 2026-10-29: A3 (#279) made the cascade atomic. See the next line.
- **The business-delete cascade is not atomic today, and A3 must not assume it is.** The writes run concurrently and outside the transaction; one Mongo transaction session doesn't take concurrent operations, so A3's unit of work has to serialise them (or Postgres's transaction does it for C4). An integration test pins the current behaviour; A3 flips it on purpose.
- **The business-delete cascade is atomic, and its work must stay safe to re-run.** It runs in one `UnitOfWork`, one write at a time. `MongoUnitOfWork` uses `withTransaction`, which re-runs the work after a write conflict, so concurrent deletes both answer 200. C4's Postgres implementation must keep both properties: roll back on any throw, and tolerate a retry.
- **Core never imports a driver type.** No `ClientSession`, no Drizzle `db` outside `repositories/`. The seam (A) is what makes F1 a deletion rather than a rewrite.
- **A write to a `jsonb` column stores the value as sent.** The Mongo pipeline-update bug that replaces `$`-prefixed strings does not carry over, and nothing may reintroduce a transformation of free text on the way in.
