# selector2 — operations

`README.md` (Database, Deploy) and `docs/admin-api.md` in the repo are the full reference. This is the short path and what bites. There is one environment, **dev**: project `ilg-merak-dev-b5e3`, region `us-central1`. There is no prod.

## Live services (snapshot 2026-11-12)
- API: `https://selector2-api-dev-qbs2p3wu5a-uc.a.run.app`
- UI: `https://selector2-ui-dev-qbs2p3wu5a-uc.a.run.app`
- Both are public at the Cloud Run layer (`allUsers` invoker) and authenticate in the app. An unauthenticated `GET /health/liveness` is 200; `GET /health/readiness` is 200 once Postgres answers and 503 otherwise.

## Deploy
- A merge to `main` touching `apps/**`, `iac/**` or the workspace files runs `deploy-dev.yaml`: `preflight`, then `docker-push` for both apps, then `terraform-apply` for both in parallel (`fail-fast: false`). Any branch deploys by hand: `gh workflow run deploy-dev.yaml --ref <branch>`.
- Pull requests that change `iac/` get a Terraform plan comment per app from `tf-plan-pr.yaml`. Read it: dev applies run on merge with no approval gate.
- **Migrations run inside the apply.** The selector2-api apply creates the Cloud Run job `selector2-api-dev-migrate` and executes it (`run_execution_token` changes every apply, so a re-run migrates again). A failed job fails the apply and the new revision never rolls; the old one keeps serving. The log line is `migrations failed`, with the database error code, under the job in Cloud Logging. Migrations only go forward, so keep one compatible with the previous image.
- The job waits up to five minutes for its first database connection, because IAM grants take a couple of minutes to reach Cloud SQL.
- Dev deploys announce failures only (`notify_on_failure: true`). Do not post deploy announcements by hand.
- Repo settings the workflows need: `DATADOG_API_KEY`, `PLATFORM_CI_APP_PRIVATE_KEY`, `SLACK_WEBHOOK_URL` (secrets) and `PLATFORM_CI_APP_ID` (variable). `_preflight` fails naming whichever is missing.

## The god account and its secret
- The migrate job syncs the `god` account's argon2id hash to `GOD_INITIAL_PASSWORD` on every run. The value is the Secret Manager secret `selector2-god-password`, generated by Terraform's `random_password.god` and **pinned to the version Terraform made**.
- Only the migrator service account can read it. The runtime accounts cannot, and Harry's own account was denied (2026-11-12). The password is also in the project's Terraform state.
- **Rotate through Terraform:** `terragrunt apply -replace=random_password.god` (or taint and deploy). A version added by hand with `gcloud secrets versions add` is not picked up.
- To read the version in use, take it from the job (`gcloud run jobs describe selector2-api-dev-migrate --region us-central1 --project ilg-merak-dev-b5e3`) and read that version, never `latest`. Do not print the value into chat, a log or a file.
- To look at the data by hand: `cloud-sql-proxy --auto-iam-authn --impersonate-service-account=<migrator>`. Anyone doing so must be in `db_migrator_impersonators`, which is empty (snapshot 2026-11-12). A direct `psql -h` to the instance is refused.

## Checking the `X-Forwarded-For` hop count
The throttle keys on the last `X-Forwarded-For` entry (one trusted hop), and a wrong count either bypasses it or locks everyone into one bucket. Re-run this black-box check after any change to what sits in front of a service. Use a username that does not exist, so no real counter moves, and a label for `$N`:

1. From one machine send 12 requests, each with a different forged left-most entry:
   `for i in $(seq 1 12); do curl -s -o /dev/null -w '%{http_code}\n' "$URL/admin/accounts" -u "throttle-probe-$N:wrong-password" -H "X-Forwarded-For: 10.0.0.$i"; done`
   Expect ten `401`, then `429`. All `401` means the forged entry is being counted (hop count too far left).
2. From a different network send one request for the same username. Expect `401`. A `429` means every caller shares one bucket (too far right).
3. The `429` carries `Retry-After` of at most 900 seconds.

On 2026-11-12 the api passed step 1 on dev (twelve bad logins gave ten 401s then 429s). On 2026-11-13, after the UI started forwarding its visitors (#23), the api passed steps 1 and 3 again plus the forwarded-visitor checks 4 to 6 in `docs/admin-api.md` (6 from one network only): ten wrong sign-ins through the ui, then the same username straight to the api from the same machine, gave 429. Step 2 and the ui's forged-entry check (`XFF_DEPTH=1`, `docs/ui.md`) are still to run.

## Carrier egress: where the mocks come from
- Each carrier's proxy is a service in `ilg-merak/carrier-playground`. selector2 calls its run.app URI, not its public name.
- `iac/projects/selector2-api/carrier-egress.tf` reads carrier-playground's `mock-edge` output `service_uris` with `terraform_remote_state` (state prefix `carrier-playground/mock-edge`, the same bucket) and sets `CARRIER_PROXY_URIS` and `CARRIER_ID_TOKEN=metadata`. `mock-edge` calls Amazon SFP `amazonsfp`; the Terraform renames it to `amazon-sfp`.
- With the output missing, the map is empty and the api falls back to the public names, `https://<carrier>.mocks.merak.freightops.dev`. selector2 picks up a change to `mock-edge` only on its own next apply.
- The mocks stay public, so the api's service account needs no invoker grant today. If they are made private, add `selector2-api-dev-cloudrun@ilg-merak-dev-b5e3.iam.gserviceaccount.com` to `mock-edge`'s `invoker_members`.
- On dev, `mock_contracts = true` in `iac/env/dev.tfvars` sets `SELECTOR2_MOCK_CONTRACTS` on the api and the migrate job. The job logs `mock contracts backfilled` with `tenants`, `tenantsFilled` and `tenantsFailed`, and `mock contracts provisioned` per tenant filled; a tenant that fails is logged with its id and never fails the job or the deploy. The first run (2026-11-13) filled god's tenant.
- Each contract's proxy key is a `fixture:<key>` reference in `carrier_account.credential_ref` (a published mock key). `secret:<name>` is refused with `credential_unavailable`, because Secret Manager is never read for carriers.
- A carrier call that fails shows as a `carrier_call` row (operation, correlation id, attempt, status, outcome, error code) and, in the UI's routes, as the call trace on a shipment.

## Observability
- Datadog service tags `selector2-api` and `selector2-ui`, with the agent in the container. Logs are JSON through pino, with `x-request-id` on every line and every response. Fixed log messages live in `apps/selector2-api/src/observability/messages.ts`. Debug level is set in dev tfvars.
- Never expect a body, label, address or key in a log. The booking-loss messages carry identifiers only: `shipment booking not recorded` (with the carrier handle, which is what cancels it), `shipment deletion not recorded`, `shipment commit not reverted`, `shipment batch interrupted`, `stale shipment booking failed`, `carrier call not recorded`.
- Startup: `database ready` or `database not ready before the deadline`. Readiness stays 503 until a connection works.

## Real failure modes
- **UI deploy before the API's state exists.** `selector2-ui`'s Terraform reads `service_uri` from selector2-api's state and fails its postcondition if it is missing. `deploy-dev` applies both in parallel, so a first apply can fail on the UI side. **ASSESSED:** a re-run succeeds once the API apply has written the state.
- **A failed migration** stops the api rolling and leaves the old revision serving, with `migrations failed` in the job log. A migration that adds a column the old image does not read is safe; a drop is not.
- **Scale-out exhausts the database.** No instance cap (R8) and a 25-connection `db-f1-micro`: the pool is 2 per instance and a deploy overlaps two revisions. Past that, readiness returns 503 and the migrator cannot connect.
- **A database that never connects does not fail a deploy.** Cloud Run probes liveness only (R9), so the instance is ready and returns 503 from readiness.
- **A booking the carrier made but selector2 did not record** comes back as `unrecorded` with the handle, consignment and parcel numbers. Cancel it with those.
- **A repeated create inside the stale limit** returns `in_progress` after an ambiguous failure. Check with the carrier before the limit passes.
- **A local plan with a developer account** gets 403 on the state object. Only `terraform-runner@ilg-merak-dev-b5e3` reads it, so read the plan from the PR comment.
- **Rate-limited sign-ins** return 429 with `Retry-After`. Through the ui the api counts each visitor's own address, but only while the ui's token verifies. A `forwarded visitor address ignored` warning (at most one a minute per reason) means it has fallen back to the ui's shared address: `other_caller` is a service-account mismatch, `wrong_audience` an audience mismatch, `keys_unavailable` (with a `cause`) Google's keys unreadable. The ui logs `api_caller_token_unavailable` when the metadata server fails.
