# Routing metadata to Firestore — read side

Paired with [[../../snap-adapter/plans/routing-metadata-to-firestore-write-side|write-side plan]] (intent, store design, and the wipe defect live there — not restated).

## Acceptance criteria
- [x] Confirmations for post-cutover orders resolve routing from Firestore: `snap.routing_lookup.hit` per confirmation type, `connectorId` on the envelope, `source` attribute on the publish. *(Live in prod — `good_out` 1473 hit, `good_in` 2 hit over 7d to 2026-09-11; R1 #211. Only good_in/good_out carry prod traffic; pick/pack/WOC/RGA proven in dev.)*
- [x] RGA confirmations have the same store-first/attachment-fallback parity as good_in/good_out/pick/pack/WOC (reversed from initial scope-parity decision — Harry, 2026-09-03: "ideally we want parity everywhere").
- [x] A Firestore reader **error** never silently degrades to broadcast: it propagates out of `mapOwnedEntries` and `QueueLane.drainForClient` catches it per consumer (logs, `snap.poll.failure`, returns `[]` for that handler this cycle — nothing claimed or published, retry next cycle; siblings on the lane unaffected). Metered as `snap.routing_lookup.error{lane}`. Only a genuine **miss** falls back to the attachment, then to the unchanged manual-origin path. *(Originally worded "aborts the poll" — wrong, corrected 2026-09-03 after review.)*
- [x] Lookups are batched per existing chunk/enrichment seam (despatch: 50/chunk; goods-in: per lane batch) — no per-record point-read on entries re-announced every poll.
- **Descoped to the follow-on (2026-09-14).** The per-type retirement-gate monitors and the post-retirement "no attachment fetch" outcome are no longer this waypoint's ACs. This waypoint delivers the read side (store-first resolution, attachment fallback intact); *retiring* the attachment — build monitors → remove the attachment **write** → drain → remove the attachment **read** (former R2) — is tracked in [[../../snap-adapter/plans/FUSE-1078-retire-routing-attachments|the attachment-retirement follow-on]].
- [x] `GoodsOutConfirmationHandler` resolves each line's Shopify `fulfillmentId` store-first (per SNAP `Line` id), falling back to the `SHL` attachment — the second data class subject to the wipe-on-retry defect (reversed from initial routing-only scope — Harry, 2026-09-03: "routing was meant to be blanket for this").

## Affected boundaries
`despatch-confirmation.handler.base.ts` (`extractRouting`, `mapConfirmation` seam, and — from R1c — the widened per-doc store-read type) + goods-out/pick/pack/WOC handlers, `goods-in.confirmation-handler.ts` (private REH variant, keyed `receipt.ReceiptId`), `receipt-confirmation.handler.base.ts` (`routingAware` flag — now `true` for RGA, still `false` for FGR), `return-goods-authorization.confirmation-handler.ts` (private REH variant, same pattern as goods-in — added 2026-09-03), `confirmations.service.ts` / `confirmation-failure.ts` (`ROUTING_AWARE_TYPES` = `good_in, good_out, return_goods_authorization, pick_confirmation, pack_confirmation, work_order_confirmation` — six, RGA added 2026-09-03), `extensions/routing.ts` (retire at R2; `line-extensions.reader.ts` tolerates the legacy key), `adapters/firestore/routing-metadata.reader.ts` (`getMany`'s value type widens for line extensions at R1c), `bootstrap/factory/controller.factory.ts`, `config/config.schemas.ts`, `iac/projects/snap-queue-polling-service/` (viewer IAM lands via the write-side plan). See [[../architecture|architecture]].

## Assumptions & uncertainty
- Routing must attach per-confirmation before `groupByCustomer` splits by `{customer}::{connectorId}::{source}` — the async `mapConfirmation` is the only per-record seam (verified at `origin/master`).
- Metrics must go through `snapMetrics` + a catalog entry in `observability/catalog/snap-polling.type.ts` to land as `snap.routing_lookup.*` in Datadog (the bare `metrics` client is un-namespaced), tagged by confirmation type.
- Branch pushes don't deploy — dev evidence via `snap-queue-polling-service-manual-deploy.yaml`.
- No backfill — drain instead (Harry, 2026-09-02). Consequence accepted: the `work_order_confirmation` gate may be held open by FUSE-1062-style stuck queue entries that re-announce indefinitely; those must be cleared (or age-excluded from the gate) before R3 can land for that type.
- Drain window: measure the true max prod create→final-confirmation lag (PO goods-in tail) during R1's soak; working assumption ≥4 weeks after W5 hits prod.
