# Routing metadata to Firestore — write side

Paired with [[../../snap-queue-polling-service/plans/routing-metadata-to-firestore-read-side|read-side plan]] (same programme, deploys independently).

## Intent
Move routing-metadata persistence (`{connectorId, source}` provenance driving confirmation routing) off SNAP attachments into a new Firestore database. Attachments are wiped by SNAP's keyed-PUT replace-children semantics: a retried/resent create re-PUTs the entity, and if that retry fails the live entity is stranded routing-less, invisibly (`apps/snap-adapter/CLAUDE.md` documents the PUT behaviour, verified GADG dev 2026-07-02/03; the retry-fail wipe is the edge case Harry reported 2026-09-02). Firestore + routing-only scope decided by Harry 2026-09-02.
~~Line extensions stay on attachments~~ — reversed 2026-09-03 (Harry: "routing was meant to be blanket for this"). Shopify's per-line `fulfillmentId` (`extensions.shopify`, written to the `SHL` attachment table by `handleShopifyLineExtensionAttachment`) is the only other data subject to the identical wipe-on-retry defect class, and only `SalesOrderService`/`GoodsOutConfirmationHandler` are involved — PO/RGA/WO/master-data carry no line extensions. Same store, same doc (merge-written, since the SNAP-assigned `Line` id is only known **after** create via a live GET, unlike routing which is known pre-create), new `lineExtensions` field. See W6.

## Acceptance criteria
- [x] Every Fuse-created SO/PO/RGA/WO produces a Firestore doc in `fuse-wms-routing` / `routing-metadata`, id `{businessId}__{entityId}`, written **before** the SNAP create (master_data skips; no-connectorId-and-no-source skips).
- [x] With `ROUTING_STORE_REQUIRED=false` (dark launch) behaviour is byte-identical to today; store failures only emit `snap.routing_store.failure`.
- [x] With `ROUTING_STORE_REQUIRED=true`, a store failure 503s (Pub/Sub redelivers) — never the `unexpected/transient:false` fall-through to `create_data_failure`; the 10th delivery attempt self-reports to `entity_error`, not the consumer-less DLT.
- [x] After W5, a new dev order carries **no** SHH/REH routing attachment yet its confirmation still routes with the correct `source` attribute (end-to-end negative control).

## Affected boundaries
`event.controller.ts` (`createSnapData` ordering + `classify-snap-failure.ts`), `ISnapService` (`snap-service.type.ts`) + the four entity services (+ `master-data` no-op), new `adapters/firestore/`, `snap.recorder.ts`/`snap-metric.type.ts` (new `routing_store.*` names — do not repoint untagged `routing_metadata.*`), `bootstrap/factory/controller.factory.ts`, `config/env/config.ts`, `docker-compose.yml` e2e harness, `iac/projects/snap-adapter/` (+ IAM in the poller's project), both `cloud-run.tf`s. See [[../architecture|architecture]].

## Assumptions & uncertainty
- SNAP keyed PUT replaces children incl. attachments — `apps/snap-adapter/CLAUDE.md` (GADG-verified) + Harry's retry-fail edge case; live repro deliberately skipped (Harry, 2026-09-02).
- Deterministic entity id is available pre-create (`parseFromCanonicalToSnap` embeds `ShipmentId`/`ReceiptId`; `createInSnap` returns it payload-derived, so `getResourceId` should reuse, not duplicate, that logic) — verified at `origin/master`.
- **No TTL** (reverses the draft): stuck queue entries re-announce indefinitely (FUSE-1062), so expiry would mis-route + spam the failure inbox; docs are a few hundred bytes.
- Named DB `fuse-wms-routing`, `europe-west2`, provisioned in `iac/projects/snap-adapter/firestore.tf`; database id as a per-project `variables.tf` default in both stacks (not `global.tfvars` — root.hcl feeds that to every project, and `iac/env/**` edits redeploy both apps). IAM: `google_project_iam_member` only (`_binding` is project-authoritative and the two states would fight); `roles/datastore.user` for `snapadapt{env}-cr`, `roles/datastore.viewer` for `snap-polling-service-{env}-cr`.
- Branch pushes do NOT deploy (`branches: [main, master]`) — dev evidence goes via `snap-adapter-manual-deploy.yaml`.
- API enablement: Harry enables `firestore.googleapis.com` manually via gcloud in both envs (decided 2026-09-02).
- No backfill — drain the fallback era instead (Harry, 2026-09-02); see read-side R2 for the per-type gate and the stuck-WOC caveat.
- ~~RGA asymmetry stays scope-parity~~ — reversed 2026-09-03 (Harry: "ideally we want parity everywhere"). The write side already stored RGA routing from W3 (`ReturnGoodsAuthorizationService.getRoutingKey` shipped with the other three entity services); the asymmetry was read-side only, and the poller now consumes it too — see read-side plan's new increment.
